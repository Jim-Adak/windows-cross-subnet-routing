# Windows Server 跨子网故障：静态路由、动态路由与地址规划对比

> 状态：**静态路由修复已实际验证；动态路由部分为原理分析与实验设计，未在原网络部署。**  
> 关联案例：[Windows Server 跨子网访问异常：静态路由修复实录](../../README.md)

## 1. 背景与已知事实

原案例中：

| 节点 | 地址 / 掩码 | 默认网关 |
| --- | --- | --- |
| Windows Server | `172.16.76.3/16` | `172.16.76.1` |
| Windows 11 | `172.16.157.222/24` | `172.16.157.1` |

Windows Server 的选路结果显示：

```text
172.16.0.0/16      On-link
0.0.0.0/0          via 172.16.76.1
```

访问 `172.16.157.222` 时，`172.16.0.0/16` 比默认路由 `0.0.0.0/0` 更具体，因此服务器将目标判断为链路内地址，而不是通过默认网关转发。

**实际成功的修复**是在 Windows Server 上增加更具体的路由：

```powershell
New-NetRoute `
  -DestinationPrefix "172.16.157.0/24" `
  -InterfaceIndex 16 `
  -NextHop "172.16.76.1" `
  -PolicyStore ActiveStore
```

新增 `/24` 路由优先于原有 `/16` 直连路由。该方案在原环境中已由使用者确认有效。

## 2. 如果改用动态路由，能否解决？

**原则上可以，但有前提：Windows Server 必须实际学习并安装指向 `172.16.157.0/24` 的路由，且下一跳可达。** 动态路由协议本身不会自动修正错误的地址规划。

假设网络中部署 OSPF，且某路由器发布了 `172.16.157.0/24`，服务器通过支持 OSPF 的路由软件建立邻接、收到该路由并成功安装到操作系统路由表，那么可能出现：

```text
172.16.0.0/16       On-link
172.16.157.0/24     via 172.16.76.1  (learned dynamically)
0.0.0.0/0           via 172.16.76.1
```

对于 `172.16.157.222`，系统优先匹配 `/24`，从而绕过 `/16` 的 On-link 判断。

### 关键限制

1. **OSPF 邻接不是凭空产生的。** 参与设备需运行兼容的 OSPF 实现、允许协议报文通信，并满足接口、区域、认证等配置要求。
2. **路由器运行 OSPF，不代表终端自动学到 OSPF 路由。** 普通 Windows 主机通常只使用本地连接路由、静态路由和默认网关；上游路由器之间的动态路由不会直接改写服务器的本机路由表。
3. **Windows Server 不是默认的 OSPF 路由客户端。** 现代 Windows Server 的 RRAS 不原生提供可直接依赖的 OSPF 功能。若确需让服务器参与 OSPF，需要评估第三方实现及其与 Windows 路由表的集成；不要假设安装软件后一定能生效。
4. **协议学到的路由还必须被安装。** 路由过滤、度量、软件实现或已有路由可能影响最终路由表。应以实际选路结果为准。
5. **下一跳仍必须可用。** 即使有正确的 `/24`，如果 `172.16.76.1` 不会转发、回程路由缺失或 ACL 阻断，通信仍可能失败。

## 3. 最长前缀匹配比“静态还是动态”更关键

对于目标 `172.16.157.222`：

| 候选路由 | 前缀长度 | 是否匹配 | 优先级说明 |
| --- | ---: | --- | --- |
| `0.0.0.0/0` | 0 | 是 | 默认路由，最不具体 |
| `172.16.0.0/16` | 16 | 是 | 比默认路由具体 |
| `172.16.157.0/24` | 24 | 是 | 三者中最具体 |

路由的来源（直连、静态、OSPF）和路由的前缀长度是不同维度。**不同前缀长度的匹配项，先比较最长前缀；度量等因素通常用于进一步选择适用的候选路径。** 因此，一条成功安装的动态 `/24` 路由同样可能覆盖 `/16` 直连匹配。

## 4. 是否应该直接修正子网掩码？

如果网络实际按 `172.16.76.0/24` 与 `172.16.157.0/24` 分成不同三层子网，且服务器所在 VLAN 的地址规划确实要求 `/24`，则将服务器配置为正确的 `/24`，可以让它自然通过默认网关访问其他网段，而无需为每个远端 `/24` 单独添加静态路由。

但**不能仅凭两台主机掩码不同，就断定服务器应改为 `/24`**。网络可能存在特殊地址规划、Proxy ARP 或其他设计。更改服务器地址掩码可能立即影响远程管理、已有业务及其他网络的可达性。

在有网络管理权限时，建议先确认：

- 服务器物理端口所在 VLAN 的实际网段和前缀；
- 默认网关接口地址及其掩码；
- 上游路由器对 `172.16.157.0/24` 的转发与回程路由；
- 防火墙/ACL 与 Proxy ARP 的配置；
- 远程管理是否有 BMC 或其他带外回滚路径。

## 5. 三种方案的适用性

| 方案 | 核心机制 | 优点 | 局限 | 本案例判断 |
| --- | --- | --- | --- | --- |
| 添加静态 `/24` 路由 | 明确指定目标前缀与下一跳 | 改动范围小、易验证 | 拓扑变化需人工维护 | **已验证成功** |
| 修正服务器掩码 | 让本机正确区分本地/远端子网 | 可能从根本上消除错误直连判断 | 必须确认网络规划，改动风险更大 | **有条件可选，未验证** |
| 让服务器学习 OSPF | 自动接收、更新更具体的路由 | 适合多路由器、拓扑变化场景 | 部署复杂，需要协议和路由表集成 | **理论可行，原环境未部署** |

对单台服务器、单个已知目标网段的故障，静态路由通常更经济。对有多台三层设备、多条路径且需要自动收敛的网络，动态路由更有价值；但多数情况下，OSPF 应主要运行在受管理的路由器之间，而不是为了修复一台终端的子网掩码问题而部署。

## 6. 建议的隔离实验：用 FRRouting 学习 OSPF 路由

不要直接在无管理权限的校园生产网络上启用 OSPF。可以在 Hyper-V、Linux 网络命名空间或虚拟机中搭建实验拓扑：

```text
Host-A ---- Router-A ===== Router-B ---- Host-B
               \  OSPF  /
```

实验步骤：

1. 使用 Linux + FRRouting 构建两台路由器，让它们在独立的实验网段建立 OSPF 邻接。
2. 在 Router-B 后面配置一个测试网段，由 Router-B 宣告。
3. 观察 Router-A 动态学习该网段，并检查其内核路由表。
4. 关闭 Router-B 的接口或撤销宣告，观察路由撤销与收敛。
5. 再加入一条不同前缀长度的静态或直连路由，验证最长前缀匹配行为。

**注意：** 如果 Host-A 是普通 Windows 主机，它仍需要正确的本地掩码或静态/默认路由指向 Router-A。仅 Router-A 与 Router-B 交换 OSPF 路由，不会自动解决 Host-A 本机误判目标为 On-link 的问题。

## 7. 排查命令

在 Windows Server 上观察实际路由选择：

```powershell
Get-NetIPConfiguration -InterfaceIndex 16
route print -4
Find-NetRoute -RemoteIPAddress 172.16.157.222
Get-NetRoute -AddressFamily IPv4
```

对比修改前后的 `DestinationPrefix`、`NextHop` 和 `InterfaceIndex`。确认端到端连接时，应分别测试 ICMP、TCP 端口及具体应用；它们并不等价。

## 8. 结论

这次故障的核心不是“没有动态路由”，而是 **Windows Server 的 `172.16.0.0/16` 直连路由覆盖了目标地址，使服务器没有使用预期的默认网关**。实际修复通过一条更具体的静态 `172.16.157.0/24` 路由完成。

如果动态路由系统能让服务器成功安装同样的 `/24` 路由，选路结果在原理上也可以被修正；但这需要额外的软件、协议邻接和网络权限，不是本次已验证的方案。

从长期网络设计看，应先核实 IP 子网规划，再决定采用正确掩码、静态路由，还是在路由器之间部署 OSPF。
