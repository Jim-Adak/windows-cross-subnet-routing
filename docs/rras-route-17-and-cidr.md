# RRAS 配置跨网段静态路由：用 /17 覆盖多个目标网段（附 CIDR 子网划分解析）

> **状态说明**
>
> - ✅ 已实测：在 Windows Server 上通过 PowerShell 为 `172.16.157.0/24` 添加静态路由，修复原有访问问题。
> - 🔎 新问题：访问 `172.16.236.53` 仍有异常，**尚未提供该目标的选路输出或验证结果**。
> - 🧪 本文 RRAS `172.16.128.0/17` 配置属于**待验证的合并方案**，不是已经在生产网络验证成功的解决方案。

## 1. 为什么想把多条路由合并？

原服务器配置：

| 项目 | 数值 |
| --- | --- |
| Windows Server | `172.16.76.3/16` |
| 子网掩码 | `255.255.0.0` |
| 默认网关 | `172.16.76.1` |
| 物理以太网接口索引 | `16`（原环境） |
| 已确认修复的远程主机 | `172.16.157.222` |
| 新发现访问异常的主机 | `172.16.236.53` |

服务器有如下路由：

```text
172.16.0.0/16   On-link
0.0.0.0/0       via 172.16.76.1
```

因此，当目标位于 `172.16.x.x` 且**没有更具体的路由**时，服务器通常匹配 `172.16.0.0/16` 直连路由，尝试在本地链路上寻找目标，而不会默认交给 `172.16.76.1`。这描述的是**路由选择行为**，并不能单独证明某个 IP 不可达的全部原因。

若把 `172.16.157.0/24` 和 `172.16.236.0/24` 都指向相同网关，是否能用更大的一个 CIDR 地址块覆盖？可以：这两个地址都在 `172.16.128.0/17` 范围内。但覆盖范围也因此显著扩大，必须评估风险。

## 2. RRAS 图形化配置（/17 方案，未实测）

> ⚠️ **先确认网络规划。** 下述 `/17` 路由将改变 `172.16.128.0` 至 `172.16.255.255` 的选路；不建议在未核实校园网 VLAN、路由、Proxy ARP、ACL 和回程路径时直接应用。保留 BMC/控制台等带外管理通道。若已经通过静态路由解决部分故障，不要仅为使用 GUI 而贸然启用或重配 RRAS。

### 2.1 打开管理控制台

在 Windows Server 中：

1. 按 `Win + R`，输入 `rrasmgmt.msc`，打开 **路由和远程访问**。
2. 若尚未安装 RRAS，可通过 **服务器管理器 → 管理 → 添加角色和功能 → 远程访问 → 路由（Routing）** 安装所需角色服务。
3. 如果服务器已在使用 RRAS，直接检查其现有配置。**不要为了新建一条路由而重置现有 RRAS 配置**。
4. 在管理控制台展开目标服务器 → **IPv4 → 静态路由（Static Routes）**；右键选择 **新建静态路由（New Static Route）**。具体菜单可能因系统语言、版本和 RRAS 状态而不同。

### 2.2 填写参数

| RRAS 字段 | 示例值 | 说明 |
| --- | --- | --- |
| Interface（接口） | 对应 `172.16.76.3` 的以太网 | 应选实际连接网关的物理接口，而不是 ZeroTier 等虚拟接口 |
| Destination（目标网络） | **`172.16.128.0`** | `/17` 网络地址 |
| Network Mask（子网掩码） | **`255.255.128.0`** | 对应前缀长度 `/17` |
| Gateway（网关） | **`172.16.76.1`** | 需要确认该网关允许转发到各目标网段 |
| Metric（跃点数） | `1`（示例值） | 不依赖低跃点数覆盖 `/16`；核心原因是 `/17` 更具体 |

该路由逻辑上表示：

```text
172.16.128.0/17 → 172.16.76.1
```

它会匹配 `172.16.157.222` 和 `172.16.236.53`，但不会匹配服务器自身的 `172.16.76.3`。

**注意：** 原先的 `172.16.157.0/24` 静态路由如果还在，它比新增的 `/17` 更具体，因此访问 `172.16.157.222` 仍会优先走 `/24`，不能据此认定 `/17` 生效或覆盖了它。

### 2.3 更稳妥的测试顺序

在不知道整个 `/17` 的实际网络规划时，建议逐级扩大范围：

1. **单 IP（优先测试）**：`172.16.236.53`、掩码 `255.255.255.255`、网关 `172.16.76.1`，即 `172.16.236.53/32`。
2. **确认目标子网确为 /24 时**：`172.16.236.0`、掩码 `255.255.255.0`。
3. **仅在确认 128–255 这一整段都应经该网关时**：`172.16.128.0`、掩码 `255.255.128.0`。

`/32`、`/24`、`/17` 是替代或逐步试验方案；不需要无目的地同时保留所有路由。

### 2.4 验证

在服务器管理员 PowerShell 执行：

```powershell
Find-NetRoute -RemoteIPAddress 172.16.157.222
Find-NetRoute -RemoteIPAddress 172.16.236.53
route print -4
```

如果 `/17` 已安装且没有更具体的匹配路由，访问 `172.16.236.53` 时预期的关键字段是：

```text
DestinationPrefix : 172.16.128.0/17
NextHop           : 172.16.76.1
InterfaceIndex    : 16
```

然后针对有问题的目标测试：

```powershell
ping 172.16.236.53
tracert -d 172.16.236.53
```

`ping` 和 `tracert` 的 ICMP 响应可能被设备或网络策略过滤；最好再测试目标**实际提供的服务**。选路正确 ≠ 业务一定可用，仍需核实上游网关、回程路由和防火墙。

### 2.5 回滚

若 RRAS 中新建的 `172.16.128.0/17` 影响其他流量，在 **IPv4 → 静态路由** 中找到对应条目，删除该条目，并再次执行：

```powershell
Find-NetRoute -RemoteIPAddress 172.16.236.53
route print -4
```

务必核对接口、目标网络、掩码和网关，**不要误删已有的 `172.16.157.0/24` 已验证路由**。是否持久保存、重启后的行为，应以当前 RRAS 配置和实际验证为准。

## 3. /16、/17、/24、/32 到底是什么意思？

CIDR 表示法中的 `/N` 代表 IPv4 地址前 **N 个比特位属于网络前缀**。IPv4 共 32 位。

| 前缀 | 子网掩码 | 用途举例 |
| --- | --- | --- |
| `/16` | `255.255.0.0` | 本例服务器当前的直连网络 |
| `/17` | `255.255.128.0` | 把一个 `/16` 等分为两个地址块 |
| `/24` | `255.255.255.0` | 指定一个较小的网段 |
| `/32` | `255.255.255.255` | 指定单个 IPv4 地址 |

本例的 `172.16.0.0/16` 包含从 `172.16.0.0` 到 `172.16.255.255` 的全部地址。

将其划分为两个 `/17` 后：

```text
172.16.0.0/16
├── 172.16.0.0/17     → 172.16.0.0   ～ 172.16.127.255
└── 172.16.128.0/17   → 172.16.128.0 ～ 172.16.255.255
```

这正是为什么两个目标 IP 都落在 `172.16.128.0/17`。

## 4. 为什么偏偏从 128 开始？

`/17` 的前 17 位为 1：

```text
11111111.11111111.10000000.00000000
   255  .   255  .   128  .    0
```

因此第三个八位组的掩码为二进制 `10000000`，也就是十进制 **128**。这个最高位把第三个八位组分成两组：

- 最高位为 `0`：十进制 `0–127`，属于 `172.16.0.0/17`。
- 最高位为 `1`：十进制 `128–255`，属于 `172.16.128.0/17`。

网络地址计算为 **IP 地址与子网掩码按位 AND（与）**。对三个地址的第三个八位组计算：

| IP | 第三个八位组（十进制） | 二进制 | 与 `10000000` 按位与 | /17 网段 |
| --- | ---: | --- | --- | --- |
| `172.16.76.3` | 76 | `01001100` | `00000000` = 0 | `172.16.0.0/17` |
| `172.16.157.222` | 157 | `10011101` | `10000000` = 128 | `172.16.128.0/17` |
| `172.16.236.53` | 236 | `11101100` | `10000000` = 128 | `172.16.128.0/17` |

例如：

```text
157      = 10011101
128 mask = 10000000
AND      = 10000000 = 128

236      = 11101100
128 mask = 10000000
AND      = 10000000 = 128
```

所以 **157 和 236 并没有变成 128**；它们只是使用 `/17` 掩码后，计算出来的**网络地址第三个八位组**均为 128。

## 5. 最长前缀匹配与整段路由的关系

对 `172.16.236.53`，如果系统存在以下候选路由：

```text
0.0.0.0/0          via 172.16.76.1
172.16.0.0/16      On-link
172.16.128.0/17    via 172.16.76.1
172.16.236.53/32   via 172.16.76.1
```

匹配时会优先选用**前缀最长**的可用路由（此处为 `/32`）；删去 `/32` 后，`/17` 比 `/16` 更具体，才会优先使用 `/17`。对 `172.16.157.222`，如果仍有 `172.16.157.0/24`，会优先于 `/17`。

**不要为了“让整个 /16 都走网关”而随意新建另一条 `172.16.0.0/16`。** 它与已有直连 `/16` 前缀相同，优先关系还会受跃点数影响，而且可能破坏真正的本地通信。若校园网实际采用 `/24` VLAN 地址规划，长期方案可能是依据管理员确认的配置纠正服务器掩码，而不是无限添加绕行路由。

## 6. 结论与验证记录

- **已证实**：`172.16.157.0/24` 通过 `172.16.76.1` 的静态路由解决过原问题。
- **地址计算已确定**：`172.16.157.222` 和 `172.16.236.53` 都属于 `172.16.128.0/17`；`172.16.76.3` 不属于该 `/17`。
- **仍待证实**：`172.16.236.53` 是否也因 `/16` 直连选路而不可达，以及校园网是否适合把整个 `172.16.128.0/17` 统一转发给 `172.16.76.1`。
- **操作建议**：先使用 `Find-NetRoute` 核实目标路由；优先用 `/32` 做低影响验证，再由实际网络规划决定是否扩大到 `/24` 或 `/17`。
